현 회사 입사 후 두 달, 매일을 9 to 9로 정신없이 보내고 있다. 그동안 맡은 일 중 하나가 스포츠 경기 점수를 관리하고 TV 화면으로 송출하는 데스크톱 앱(Electron + Next.js)의 검도 스코어보드 API 연동이었다. 작업을 시작할 당시 검도 스코어보드는 서버 API 연동 없이 오로지 로컬에서만 동작하는 상태였다. <br /> 고객사 대상으로 기능 시연을 위해 이전 개발자분이 빠르게 작성한 코드라고만 전해 들었다. 그런데 나는 기능을 먼저 얹는 대신 상태 구조 전체를 먼저 리팩터링하는 길을 택했다. 이 글은 왜 그 선택을 했고 무엇을 바꿨는지에 대한 기록이다.

## TL;DR

- 직전에 작업한 유도 스코어보드에서 클라이언트 상태와 서버 상태의 정합성 버그를 반복적으로 겪었다.
- 검도는 아직 API 연동 전이었고, 단일 store(약 990줄)에 모든 상태와 액션이 뭉쳐 있어 인지부하가 컸다.
- 정합성 문제의 원인은 "손으로 따로 맞춰줘야 하는 상태가 여러 개"라는 데 있었다. 그래서 API를 붙이기 전에 직접 갱신하는 상태를 '점수 이벤트 리스트' 하나로 줄이고, 승패나 진행 상태 등 나머지는 거기서 계산(derive)되도록 바꿨다.
- 그 위에 로컬/서버를 같은 인터페이스로 다루는 **Repository 패턴**과 **optimistic update**를 얹었다.
- 결과적으로 API 연동 이후에도 유도에서 겪은 정합성 버그를 같은 유형으로 재발시키지 않았다.

## 유도에서 먼저 데인 경험

입사 첫 주에 맡은 첫 작업이 같은 앱의 유도 스코어보드에 단체전을 지원하는 일이었다. 단체전은 한 경기가 여러 체급의 서브매치로 이뤄지고, 그 결과를 합산해 팀 승패를 가리는 새 기능이었다. 승자결정 모달이나 서브매치 단위 네비게이션을 새로 붙이는 동시에, 기존 단체전 흐름에서 터지던 버그들도 함께 잡아야 했다.

그때 가장 많은 시간을 잡아먹은 건 기능 자체가 아니라 _상태 정합성_ 이었다. 매치를 이동하면 이전 경기의 상태가 화면에 잔류하거나, 특정 득점을 처리하면 팀 점수가 엉뚱하게 초기화되는 식의 버그가 끊이지 않았다.

원인을 들여다보면 패턴이 같았다. 화면에 필요한 값들, 즉 점수, 승패, 팀 승수, 진행 상태를 제각각 따로 들고 있으면서, 사용자가 버튼을 누를 때마다 그 값들을 하나하나 손으로 갱신하고 있었다. 갱신해야 할 곳을 한 군데라도 빠뜨리면 값들 사이가 어긋났다. 게다가 서버라는 또 하나의 저장소까지 같은 값을 들고 있으니, 맞춰줘야 할 짝이 더 늘어났다. 버그를 하나 잡아도 비슷한 게 다른 화면에서 다시 튀어나오곤 했다.

### 실제로 단체전 상태는 이렇게 흩어져 있었다

추상적으로 들릴 수 있으니 구조를 코드로 옮겨 보자(이름은 읽기 좋게 단순화했다). 단체전에서 서브매치 하나의 상태는 사실상 세 곳에 복제돼 있었다. 화면이 보는 로컬 목록, 그 안에 끼워진 서버 스냅샷, 그리고 대회 전체 경기 목록이다. 서브매치 하나의 상태를 바꾸려면 이 세 곳을 전부 손으로 맞춰야 했다.

```js
// 상태 하나 바꾸는 데 같은 값을 세 번 갱신
const updated = subMatches.map((m, i) =>
  i === activeIndex ? { ...m, status } : m
);

store.set({
  subMatches: updated, // ① 화면이 보는 로컬 목록
  match: { ...match, subMatches: updated }, // ② 그 안의 서버 스냅샷
});
contestStore.set({
  /* 대회 전체 목록에도 같은 갱신 반복 */
}); // ③
```

세 곳을 동시에 써야 한다는 걸 코드가 스스로 인정하고 있던 셈이다. 게다가 ②의 서버 스냅샷은 새로고침 때만 갱신돼서, 그 사이 로컬 변경분이 빠진 낡은 상태가 되기 쉬웠다. 그래서 화면에서 읽을 때 둘을 다시 합쳐주는 어댑터까지 따로 있어야 했다.

```js
// 읽을 때마다 로컬 값과 서버 스냅샷을 다시 합치는 어댑터
const merged = mergeLocalInto(snapshot, localSubMatches);
```

팀 승수도 마찬가지였다. 원래는 득점할 때마다 팀 승수를 직접 더하고 빼는 방식이었는데, 그 연산이 깨지기 쉬웠다. 이게 바로 "특정 득점 시 팀 점수가 엉뚱하게 초기화되던" 버그의 진원지였다.

여기에 컴포넌트 쪽에도 또 다른 상태가 있었다. 득점 이펙트를 띄우려고 store의 점수를 컴포넌트 안에서 `useRef`로 한 번 더 그림자처럼 들고 있었다.

```js
// store 점수를 컴포넌트 ref에 복제해 직전 값과 비교
const prevScore = useRef(0);
const prevMatchId = useRef('');
// 경기를 넘길 때 이 ref들이 리셋되지 않으면
// → 이전 경기의 상태가 다음 화면에 잔류한다
```

결국 "누가 몇 점이고 누가 이겼는가"라는 하나의 사실이 로컬 목록, 서버 스냅샷, 대회 목록, 컴포넌트 ref까지 네 군데에 흩어져 있었다. 하나를 바꿀 때 나머지를 빠짐없이 맞추는 건 사람이 할 일이 아니었고, 실제로 자주 어긋났다.

> 정합성 문제의 본질은 "어긋난 값들을 부지런히 맞추는 것"이 아니라 "손으로 맞춰야 할 값의 개수를 애초에 줄이는 것"에 있다. 이 교훈을 검도에서는 처음부터 적용하고 싶었다.

유도 단체전을 마무리하고 검도 스코어보드를 맡은 건 그로부터 약 3주 뒤, 아직 입사 한 달이 채 되지 않은 시점이었다. 작업 시작 당시 검도 스코어보드의 상태는 이랬다.

- **API 연동 없음.** 서버와 주고받는 로직 없이, 로컬에서만 점수를 더하고 빼는 비즈니스 로직만 존재했다.
- **단일 zustand store.** 모든 상태값과 액션 함수가 약 990줄짜리 store 하나에 뭉쳐 있었다. 점수, 타이머, UI 상태, 매치 정보가 한곳에서 섞여 무엇이 어디서 바뀌는지 추적하기 어려웠다.
- **prop drilling.** 컴포넌트들이 상태를 props로 깊게 내려받아, 데이터 흐름이 한눈에 들어오지 않았다.

여기에 곧 서버 API를 붙여야 했고, 시간은 넉넉하지 않았다. 검도 스코어보드에 처음 손을 댄 날부터 핵심 작업을 마무리하기까지 주어진 기간은 약 2주, 영업일로 따지면 열흘 남짓이 전부였다. 선택지는 둘이었다. (1) 일단 API부터 연동하고 문제는 나중에 잡는다. (2) 연동 전에 상태 구조부터 바로잡는다.

솔직히 (2)는 쉽게 내릴 수 있는 결정이 아니었다. 열흘짜리 일정에서 앞쪽 며칠을 화면에 보이는 결과물이 하나도 없는 구조 작업에 쓴다는 뜻이고, 리팩터링이 예상보다 길어지면 정작 납품해야 할 API 연동에 쓸 시간이 사라질 위험이 있었다. 당장 돌아가는 코드에 API만 얹으면, 적어도 며칠 안에 '되는 것처럼' 보이게 만들 수는 있었다.

그럼에도 (2)를 택한 건 유도에서의 경험 때문이었다. '따로 노는 상태가 여러 개'인 구조에 서버라는 저장소를 하나 더 추가하는 순간, 유도에서 겪은 정합성 지옥이 검도에서 그대로 재현될 게 분명했다. 그 지옥을 열흘 안에 디버깅으로 메우는 것보다, 앞단에서 구조를 줄여 버그가 생길 자리 자체를 없애는 편이 결국 더 빠르다고 판단했다. 일정이 짧을수록 오히려 '돌아가는 것처럼 보이는 코드'에 시간을 흘려보낼 여유가 없었다.

## 방향: 직접 바꾸는 상태를 하나로 줄이고, 나머지는 계산한다

리팩터링의 핵심 아이디어는 단순하다. 직접 수정하는 상태를 단 하나, 즉 '점수 이벤트 리스트'로 줄이고, 나머지 화면 상태는 전부 그 리스트로부터 계산한다. 검도 경기는 결국 "득점/반칙 이벤트의 시퀀스"다. 그 시퀀스만 붙들고 있으면 승패, 진행 상태, 득점 마커는 전부 그로부터 도출되는, 결과적인 값일 뿐이다.

코드로 보면 차이는 이렇다. 핵심은 "승패를 직접 set 하느냐, 이벤트로부터 계산하느냐"이다.

```js
// 이전 — 점수도 바꾸고, 승패도 손으로 바꾼다 (맞춰야 할 값이 둘)
function addPoint() {
  state.redScore += 1;
  if (state.redScore >= 2) state.winner = 'red'; // 빠뜨리면 어긋남
}

// 이후 — 이벤트만 추가한다. 승패는 "계산"될 뿐 직접 건드리지 않는다
function addPoint() {
  state.events.push({ player: 'red', type: 'point' });
}
const winner = deriveWinner(state.events); // 항상 events가 기준
```

오해를 막기 위해 분명히 해두면, 이렇게 해도 클라이언트는 여전히 서버 상태를 zustand에 들고 있다. 점수 이벤트 리스트도, 거기서 계산된 승패도 store에 저장된다. 달라진 건 "보관하느냐"가 아니라 "직접 손으로 갱신하는 상태가 몇 개냐"다. 그 결과 서버와 맞춰야 하는 대상도 사실상 리스트 하나로 줄어든다.

이 방향을 네 단계로 나눠 진행했다.

### 1. 단일 store를 도메인별 slice로 분해

약 990줄의 거대한 store를 책임별로 쪼갰다. 점수, 타이머, 매치, UI 상태, 설정이 각자의 파일로 분리됐고, store는 이들을 조립하는 얇은 진입점만 남았다.

```js
// 이전 — 모든 상태와 액션이 한 store에 (약 990줄)
const useStore = create((set, get) => ({
  scores: [],
  timer: 0,
  matchInfo: null,
  isModalOpen: false,
  enableBuzzer: true,
  addScore: (data) => {
    /* ... */
  },
  tick: () => {
    /* ... */
  },
  openModal: () => {
    /* ... */
  },
  // ... 점수, 타이머, 매치, UI가 뒤섞인 채 수십 개가 더 이어진다
}));
```

```js
// 이후 — 도메인별 slice로 나누고, store는 조립만 한다
const useStore = create((set, get, store) => ({
  ...createScoreSlice(set, get, store), // 점수 저장/삭제/동기화
  ...createTimerSlice(set, get, store), // 타이머 상태/액션
  ...createMatchSlice(set, get, store), // 현재 매치 데이터
  ...createUiStateSlice(set, get, store), // 클라이언트 UI 상태
  ...createSettingsSlice(set, get, store), // 사용자 설정
}));

// 각 slice는 자기 도메인의 상태와 액션만 안다
export const createScoreSlice = (set, get) => ({
  scores: [],
  addScore: (data) => {
    /* 점수 도메인 로직만 */
  },
});
```

코드량으로 보면 변화가 분명하다. 989줄짜리 단일 store 파일은 slice들을 조립하기만 하는 88줄짜리 진입점으로 줄었고, 실제 로직은 점수(약 300줄), 타이머, 매치, UI 상태 등 도메인별 slice 파일로 흩어 옮겨졌다. 전체 코드량이 줄었다기보다, 한 파일에 뭉쳐 있던 책임이 "무엇을 바꾸면 어디를 보면 되는지"가 분명한 단위로 나뉜 것이다.

### 2. 컴포넌트의 prop drilling 제거 및 직접 store 구독

store를 도메인별로 나눈 김에, 컴포넌트가 그 상태를 받아 쓰는 방식도 손봤다. prop drilling을 걷어내고 필요한 상태를 컴포넌트가 직접 구독하게 바꾼 것이다. 판단의 근거는 단순했다. 이 컴포넌트들은 애초에 검도 화면 전용이라 다른 곳에 재사용할 일이 없는데, 그런 컴포넌트에 상태와 액션을 props로 길게 주입하는 건 재사용성이라는 명분도 없이 중간 경유지만 늘리는 일이었다. 컴포넌트 이름부터 이미 도메인이 박혀 있으니, 필요한 상태는 부모를 거치지 않고 자기가 직접 store에서 집어 오면 된다. 실제로 점수 컨트롤 컴포넌트는 부모로부터 열 개가 넘는 props를 받고 있었다.

```tsx
// 이전 — 부모가 store 값을 props로 길게 주입
<KendoPlayerControls
  team="red"
  penalties={store.redPlayer.penalties}
  pointsCount={store.redPlayer.points.length}
  matchEnded={store.matchEnded}
  isWinner={store.winner === 'red'}
  onAddScore={store.addScore}
  onUndoScore={store.undoLastScore}
  onAddPenalty={store.addPenalty}
  // ... 상태와 액션이 십수 개 더 이어진다
/>
```

```tsx
// 이후 — 진짜 바깥에서 와야 하는 값(team)만 받고, 나머지는 직접 구독
<KendoPlayerControls team="red" />;

const KendoPlayerControls = ({ team }) => {
  const { player, matchEnded, winner, addScore, addPenalty } = useStore(
    useShallow((s) => ({
      player: team === 'red' ? s.redPlayer : s.whitePlayer,
      matchEnded: s.matchEnded,
      winner: s.winner,
      addScore: s.addScore,
      addPenalty: s.addPenalty,
    }))
  );
  // ...
};
```

이렇게 바꾸자 컴포넌트에 남는 prop은 '어느 쪽인가(team)'처럼 정말로 바깥에서 와야 하는 값뿐이고, 나머지는 컴포넌트가 자기에게 필요한 상태를 store에서 직접 집어 온다. 이 정리 한 번에 page 컴포넌트에서 props를 엮던 코드가 120줄 넘게 사라졌다. 결과적으로 어떤 화면이 어떤 상태에 의존하는지가 props 체인을 따라가지 않아도 컴포넌트 안에서 바로 읽힌다.

### 3. 점수 이벤트로부터 화면 상태를 계산하는 파생 함수 도입

점수 이벤트 리스트를 기준으로 삼고, 화면이 필요로 하는 값들을 그로부터 계산하는 순수 함수들을 만들었다. 예를 들어 "지금 경기 상태가 무엇인가(승패/진행/연장)"는 점수 시퀀스를 훑어 도출한다.

```js
// 점수 이벤트들 → 경기 상태 (순수 함수, 같은 입력이면 항상 같은 결과)
// 상태값: BEFORE_MATCH | IN_PROGRESS | LEFT_WIN | RIGHT_WIN | BOTH_LOSE | DRAW
function deriveStatus(events) {
  const winner = findWinner(events); // 2점 선취 등 검도 룰 적용
  if (winner === 'red') return 'LEFT_WIN'; // 홍(좌) 승
  if (winner === 'white') return 'RIGHT_WIN'; // 백(우) 승
  if (events.length > 0) return 'IN_PROGRESS';
  return 'BEFORE_MATCH';
}
```

이렇게 하면 서버에서 이벤트 리스트를 다시 받아오기만 해도 같은 화면이 그대로 복원된다. 화면 상태를 따로 보관하거나 복구할 필요 없이, 리스트만 맞으면 나머지는 자동으로 따라온다. 이것이 나중에 정합성 버그를 막는 토대가 됐다.

### 4. 로컬/서버를 같은 인터페이스로 묶는 Repository 패턴

그런데 왜 로컬 구현이 따로 필요할까. 여기서 '로컬'은 API 연동 없이 mock 데이터만으로 스코어보드를 돌려 보는 시연용 모드다. 애초에 내가 맡기 전의 코드 자체가 고객사 시연을 위해 만들어진 로컬 전용 코드였고, 서버를 붙인 뒤에도 이 시연 모드는 그대로 살아 있어야 했다. 그러니 로컬은 잠깐 쓰고 버릴 테스트용 stub이 아니라 계속 유지해야 하는 동작 모드이고, 서버 구현과 같은 계약으로 묶어 두면 둘이 갈라지지 않고 자연스럽게 공존한다.

마지막으로 "데이터를 어디서 가져오는가(로컬인가 서버인가)"라는 분기를 하나의 인터페이스 뒤로 숨겼다. 두 구현이 똑같은 메서드 모양을 갖도록 강제하고, 어떤 구현을 쓸지는 한 곳에서만 결정한다.

```ts
// 로컬 / 서버 구현이 똑같이 따라야 할 계약
interface ScoreRepository {
  getScores(matchId): Promise<Score[]>;
  saveScore(matchId, data): Promise<Score>;
  deleteScore(matchId, scoreId): Promise<void>;
}

// 어떤 구현을 쓸지 결정하는 단 하나의 지점
function selectRepository(source) {
  if (source === 'local') return localRepo;
  return serverRepo;
}
```

두 구현은 계약만 같을 뿐 속은 완전히 다르다. 로컬은 메모리 안에서 끝나고, 서버는 같은 동작을 API 호출로 옮길 뿐이다.

```js
// 로컬 — 메모리에서 처리
const localRepo = {
  getScores: (matchId) => store.get(matchId) ?? [],
  saveScore: (matchId, data) => store.add(matchId, data),
  // ...
};

// 서버 — 같은 모양을 API 호출로
const serverRepo = {
  getScores: (matchId) => api.get(`/matches/${matchId}/scores`),
  saveScore: (matchId, data) => api.post(`/matches/${matchId}/scores`, data),
  // ...
};
```

그래서 점수를 다루는 store 코드에는 `if (로컬) ... else ...` 같은 분기가 없다. 현재 매치의 출처(`source`)로 활성 repo를 한 번 고른 다음, 로컬이든 서버든 똑같은 메서드를 부르기만 한다.

```js
// 호출부는 local인지 server인지 모른다. 활성 repo를 한 번 고르고 같은 메서드를 호출
const repo = selectRepository(currentMatch.source);

const scores = await repo.getScores(matchId); // 읽기
const saved = await repo.saveScore(matchId, data); // 저장 (저장된 dto를 그대로 반환)
await repo.deleteScore(matchId, scoreId); // 삭제
```

로컬 repo면 이 호출들이 메모리 Map 안에서 끝나고, 서버 repo면 같은 호출이 API 요청으로 나간다. 호출하는 쪽 코드는 한 글자도 달라지지 않는다. 바로 다음에 다룰 optimistic update도 이 `repo.saveScore(...)` 한 줄을 감싸는 형태라, 로컬/서버 양쪽에 똑같이 적용된다.

덕분에 점수를 다루는 코드는 로컬인지 서버인지 신경 쓰지 않는다. 같은 호출 한 줄이면 끝이고, 데이터를 저장하지 않는 시연용 로컬 모드도 같은 계약 안에 자연스럽게 들어온다. 이 통합으로, 기존에 온라인과 오프라인 구현이 따로 갈라져 있던 구조가 사라졌다.

## 그다음에야 API를 붙였다

위 네 단계가 끝난 뒤에야 API 연동을 진행했다. 그런데 서버를 붙이고 나니 새로운 문제가 생겼다. 처음에는 점수 버튼을 누르면 서버에 저장 요청을 보내고, 그 응답을 받은 뒤에야 리스트를 갱신했다. 그러다 보니 버튼을 눌러도 득점 마커가 화면에 곧장 뜨지 않고, 서버 응답이 돌아온 다음에야 한 박자 늦게 나타났다. 정확히 계측하진 않았지만, 개발자 도구 Network 패널에서 저장 요청이 끝나기를 기다리는 동안 마커가 뜨지 않고 멈춰 있는 게 눈에 보일 정도였다. 점수를 빠르게 연달아 넣는 심판 입장에서는 거슬리는 지연이었다.

그래서 적용한 게 optimistic update다. 사용자가 점수 버튼을 누르면, 서버 응답을 기다리지 않고 임시 항목을 리스트에 먼저 끼워 넣어 화면을 즉시 갱신한다. 그리고 서버가 진짜 데이터(정식 id 포함)를 응답하면 그 임시 항목을 실제 데이터로 교체(reconcile)하고, 실패하면 되돌린다(revert). 화면 반영이 더 이상 네트워크 왕복에 묶이지 않고 다음 렌더에 바로 일어나므로, 왕복 시간만큼 끌리던 체감 지연이 사실상 사라진다.

| ------------------ | ----------------------------------------- | ------------------------------------ |
| 직접 갱신하는 상태 | 점수, 승패, 팀 승수, 진행 상태 등 여러 개 | 점수 이벤트 리스트 하나              |
| 나머지 화면 상태   | 각각 손으로 set                           | 이벤트로부터 계산(derive)            |
| store              | 단일 store 약 990줄                       | 도메인별 slice로 분해                |
| 데이터 출처        | 로컬/서버 분기 산재                       | 단일 Repository 인터페이스 + 결정점  |
| 서버와의 정합성    | 값마다 따로 동기화 → 잦은 drift           | 리스트 하나만 reconcile → drift 차단 |

## 왜 TanStack Query를 도입하지 않았나

API를 붙이는 단계에서 TanStack Query 도입도 진지하게 검토했다. 서버 상태를 다루는 표준 도구이고, optimistic update도 기본으로 지원하기 때문이다. 그런데 따져볼수록, 이 프로젝트에는 맞지 않는다는 결론에 도달했다.

**첫째, 정작 내가 아쉬웠던 문제를 TanStack Query가 풀어주지 않는다.** 검도에서 한 번의 득점 액션은 사실 두 번의 쓰기로 이뤄진다. 점수를 기록하는 호출과, 그 결과로 승패를 결정하는 호출이다.

```js
// 한 번의 득점 = 두 번의 서버 쓰기.
// 승패는 클라이언트가 이벤트로부터 이미 계산해 두므로 ②가 ①의 응답을
// 기다릴 필요가 없다. 그래서 원리적으로는 이렇게 병렬로 쏠 수도 있다.
await Promise.all([
  recordScore(...), // ① 점수 기록
  updateMatchStatus(...), // ② 이미 계산된 승패를 갱신
]);
```

실제 구현에서는 중복 호출을 막는 가드 때문에 두 쓰기가 순차로 나가지만, 승패를 클라이언트가 직접 계산하므로 병렬화 자체는 가능하다. 어느 쪽이든 진짜 문제는 이 둘이 한 트랜잭션이 아니라는 점이다. 한쪽이 성공하고 다른 쪽이 실패하면, 서버에는 점수만 기록되고 승패는 갱신되지 않은(혹은 그 반대의) 어중간한 상태가 남는다. 병렬화는 지연시간을 줄여줄 뿐, 이 부분 실패 창 자체를 없애주지는 않는다.

그런데 optimistic update는 본질적으로 하나의 쓰기를 되돌리는 패턴이고, TanStack Query가 제공하는 optimistic update도 mutation 단위다. 두 호출을 하나의 mutation으로 묶어 `mutationFn: () => Promise.all([...])`로 감싸도 마찬가지다. `Promise.all`이 reject돼도 이미 성공 응답으로 커밋된 한쪽 서버 쓰기는 되돌아가지 않는다. TanStack Query의 `onError` 롤백은 클라이언트 캐시(낙관적 패치)를 되돌릴 뿐, 서버 상태를 보상(compensate)해주지는 않기 때문이다. 결국 "①은 이미 커밋됐는데 ②만 실패한" 상태의 원자성은 도구를 바꿔도 그대로 남는다. 즉 이건 클라이언트 상태 도구의 문제가 아니라 백엔드 API 계약의 문제이고, 호출을 병렬로 하든 한 mutation으로 묶든 사라지지 않는다.

**둘째, 이 화면은 TanStack Query가 빛나는 환경이 아니다.** TanStack Query는 서버 캐시가 무거운 앱에서 강하다. 독립적인 쿼리가 많고, 중복 요청을 합치고, 여러 화면이 같은 서버 데이터를 공유 구독하는 상황 말이다. 물론 이 스코어보드에도 서버를 다시 읽어야 하는 지점은 있다. 어드민이 경기 순서를 바꾸거나 상태를 직접 조작할 수 있어서, 매치를 전환하거나 새로고침할 때 매치 리스트와 점수를 다시 가져온다. 하지만 이건 백그라운드 폴링이나 window-focus refetch처럼 TanStack Query가 자동으로 해주는 종류가 아니다. 매치 전환이라는 명시적 경계에서 "서버 상태 갱신 → 이동할 매치 결정 → 상세와 점수 fetch"를 순서대로 엮어야 하는, 오히려 직접 짠 절차적 흐름이 더 잘 맞는 자리다. 그나마도 데이터를 소비하는 화면이 사실상 하나뿐이라 공유 캐시가 주는 이점도 거의 없다.

**셋째, 같은 앱 안의 다른 종목들과 기술 스택이 어긋난다.** 이 데스크톱 앱에는 검도 말고도 유도, 레슬링 같은 다른 종목 스코어보드가 함께 들어 있고, 이들은 모두 zustand로 클라이언트와 서버 상태를 함께 다룬다. 프로젝트 전체에서 TanStack Query를 쓰는 곳은 한 군데도 없다. 여기서 검도에만 TanStack Query를 들이면, 같은 앱 안에서 종목마다 서버 상태를 다루는 방식이 갈린다. 사실상 한 사람이 전 종목을 오가며 유지보수하는 코드베이스에서, 도메인마다 상태 도구가 다른 건 그 도구가 주는 이점보다 오가는 비용이 더 큰 선택이었다.

대신 필요한 optimistic 동작은 작은 헬퍼로 직접 구현했다. 라이브러리 없이도 단일 쓰기의 즉시 반영과 되돌림은 충분히 다룰 수 있었다. 다만 위에서 짚은 두 호출의 원자성 한계는 분명히 남아 있다. 이건 라이브러리로 덮을 게 아니라, 점수 기록과 승패 결정을 하나의 트랜잭션 엔드포인트로 합치는 백엔드 변경으로 푸는 게 맞다고 본다. 실제로 승리 결정 경로는 이미 두 번의 쓰기를 한 번의 PUT로 합쳐 같은 문제를 줄여둔 상태이고, 일반 득점 경로까지 같은 방향으로 정리하는 것이 다음 과제다.

## 결론

기능을 더 얹기 전에 기반 구조부터 바로잡는 선투자는 당장은 돌아가는 길처럼 보이지만, 열흘 남짓한 일정 안에서도 한 번 데어본 문제를 다른 도메인에서 또 만나지 않으려면 오히려 빠른 길이었다. 정합성 문제의 해법은 결국 "어긋난 값들을 부지런히 맞추는 것"이 아니라 "손으로 맞춰야 할 값의 개수를 줄이는 것"이었다. 직접 바꾸는 상태를 하나로 좁히고 나머지를 계산되게 만들자, API 연동 이후에도 값들이 어긋날 자리가 크게 줄었다.

유도에서 같은 버그를 반복해 잡던 경험이 없었다면 API부터 붙이는 길을 택했을지도 모른다. 같은 고통을 두 번 겪지 않으려던 판단이 결과적으로 가장 큰 레버리지였다.
